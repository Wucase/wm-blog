# WM Blog Rules

## Overview

在 `wm-blog` 项目中开发时，始终把这份规则当作默认约束。
目标不是堆规则，而是保证项目后续可扩展、可维护、样式可统一管理。

## Core Rules

### 1. Use modular development

- 按功能拆分代码，不把页面、状态、请求、工具函数和样式逻辑混在一个文件里。
- 优先按职责放置文件，例如：
  - `views/` 放页面
  - `components/` 放可复用组件
  - `stores/` 放 Pinia 状态
  - `router/` 放路由
  - `utils/` 或 `services/` 放请求封装和通用能力
- 单个文件过大时，主动继续拆分，而不是等到后期再重构。
- 新增功能时，优先考虑是否可以复用已有模块，避免重复实现。

### 2. Add Chinese comments where they provide value

- 代码注释统一使用中文。
- 不写低价值注释，例如“给变量赋值”“调用函数”这类显而易见的描述。
- 只在这些场景添加注释：
  - 模块职责说明
  - 复杂逻辑说明
  - 状态流转说明
  - 接口字段或边界条件说明
  - 样式分区说明
- 注释要短、准、直接，优先帮助后来维护的人快速理解代码。

### 3. Centralize CSS variables

- 可复用的视觉值不要直接散落在组件或页面里，统一抽到 CSS 变量中。
- 优先抽离这些变量：
  - 主题色
  - 字体大小
  - 文本颜色
  - 背景色
  - 边框色
  - 圆角
  - 阴影
  - 间距
- 变量名保持语义化，例如：
  - `--color-primary`
  - `--color-text-primary`
  - `--font-size-base`
  - `--radius-lg`
- `--shadow-card`
- 若项目后续出现主题系统，优先在全局样式或专门的 token 文件里维护这些变量。

### 4. Build responsive layouts for different devices

- 页面必须考虑多设备适配，不能只针对桌面端编写样式。
- 至少覆盖这些场景：
  - 桌面端
  - 平板横屏
  - 平板竖屏
  - 手机端
- 响应式适配时，优先调整这些内容：
  - 布局列数
  - 区块间距
  - 字号和行高
  - 卡片尺寸
  - 图片或视觉元素位置
  - 按钮点击区域
- 如果页面包含动画、悬浮位移或鼠标交互，还要考虑触屏设备的表现：
- 触屏设备优先保证稳定和可点击
- 必要时关闭 hover 依赖或鼠标位移效果
- 不允许只做到“宽度缩小还能显示”，而要保证不同设备下仍然有清晰层级和可读性。
- 响应式代码优先写在组件自己的样式中；全局断点、尺寸变量可放到全局样式或 token 文件统一维护。

### 5. Use the project breakpoint convention by default

- 新页面或重构页面时，优先使用这组断点进行适配：
  - `max-width: 1200px`
  - `max-width: 1080px`
  - `max-width: 960px`
  - `max-width: 720px`
  - `max-width: 560px`
- 这些断点的建议用途：
  - `1200px`：桌面大屏到平板横屏的过渡调整
  - `1080px`：首屏或复杂双栏区域开始收缩
  - `960px`：内容区从多列转单列的重要断点
  - `720px`：手机主适配断点
  - `560px`：小屏手机细节修正
- 如果某个页面更复杂，可以新增断点，但默认先复用这套约定，避免项目里断点体系混乱。
- 断点调整应配合间距、字号、卡片尺寸和视觉元素位置一起修改，不要只改 `grid-template-columns`。

### 6. Consider all project roles during feature design

- `wm-blog` 不是单一访客站点，默认包含三类角色：
  - 游客
  - 普通用户
  - 管理员
- 设计页面、路由、状态和接口调用时，默认要先判断当前功能属于哪一类角色使用。
- 游客相关功能通常包括：
  - 首页浏览
  - 文章阅读
  - 分类或标签查看
  - 登录和注册入口
- 普通用户相关功能通常包括：
  - 登录后个人中心
  - 收藏、评论、互动
  - 个人资料维护
  - 用户侧内容管理
- 管理员相关功能通常包括：
  - 内容发布与编辑
  - 分类、标签、评论管理
  - 用户管理
  - 站点配置与首页配置
- `homeViewSetting` 默认视为管理员页面，不属于游客或普通用户可见范围。
- 与站点配置相关的数据，默认按服务端持久化处理；前端负责读取、编辑、提交和回显，不把正式配置只保存在浏览器本地。
- 如果新增页面或模块，优先在命名、目录和权限边界上区分角色，不把游客页、用户页、管理页混在同一个职责不清的模块里。
- 如果后续接入权限系统，前端结构也要为角色区分预留扩展空间，例如独立路由分区、独立布局或独立菜单。

### 7. Keep home page and admin home settings aligned

- 首页是游客进入 `wm-blog` 后首先看到的核心展示页，默认路由为 `/wm`。
- 首页默认包含这些基础模块：
  - 顶部导航
  - 首屏欢迎区
  - 推荐内容区
  - About 介绍区
  - 底部备案信息
- 首页文案和图片默认按“可配置”来设计，不要把最终内容硬编码死在组件内部。
- 首页展示数据默认通过服务层统一读取，支持 mock 数据与真实后端接口切换。
- 首页相关数据结构应集中管理，优先通过独立类型、mock 数据文件和 service 层维护，而不是散落在多个组件里。
- 首页组件应尽量做成“只负责展示”的结构，业务数据读取、映射和持久化逻辑放在页面层或 service 层。
- 管理员首页设置页默认路由归属于管理员分区，例如 `/wm/admin/home-view-setting`。
- 管理员首页设置页不是独立后台表单页，而应尽量保持与首页结构一致，让管理员以接近所见即所得的方式进行编辑。
- 管理员首页设置页的目标是编辑首页，而不是重新定义另一套布局；新增配置能力时，优先复用首页已有模块和组件。
- 首页设置相关数据默认保存在服务端；mock 模式可以使用本地兜底，但正式环境必须以服务端配置为准。
- 首页和首页设置页共用数据结构时，优先维护统一类型定义，避免“展示页一套字段，设置页另一套字段”。
- 如果首页新增模块，例如分类入口、文章流、公告区、Banner 区，对应的管理员配置能力也要同步考虑是否需要补充。
- 首页的图片、文字、按钮、链接等内容，如果已经被定义为可配置项，则前端实现时默认要支持：
  - 读取当前配置
  - 编辑当前配置
  - 回显最新配置
  - 提交保存配置
- 首页设置页中的文字编辑，默认采用原地编辑思路：
  - 当前文字可直接切换成输入框或文本域
  - 管理员修改后单独保存
  - 取消时恢复到进入编辑前的内容
- 首页设置页中的图片编辑，默认采用所见即所得思路：
  - 重新上传后先本地替换预览
  - 保存时再提交到服务端
- 首页设置页中的编辑控件要尽量轻量，不破坏首页原有布局：
  - hover 时再显示
  - 尽量不占据正常内容流
  - 不影响首页视觉层级
- 如果某个编辑入口存在点击不稳定、hover 命中区域过小或按钮遮挡内容的问题，优先保证“稳定可编辑”，再去优化视觉精致度。

### 8. Standardize mock data and API service logic

- 页面开发时，默认同时考虑 mock 数据模式和真实接口模式，不把页面写成只能吃本地常量或只能吃后端接口中的一种。
- 页面层职责要保持简单：
  - 负责加载状态
  - 负责触发 service 调用
  - 负责把数据传给组件
  - 不在页面里直接堆复杂的 mock 判断和接口映射细节
- mock 数据优先放在 `src/data/` 中集中维护，不直接散落在组件或页面里。
- mock 数据文件默认应包含：
  - 数据常量
  - mock 异步方法
  - 数据标准化方法
- 如果页面已有类型定义，则 mock 数据必须尽量严格对齐类型，而不是随意拼对象。
- 请求逻辑优先放在 `src/services/` 中封装，页面和组件不直接写 axios 细节。
- service 层默认负责：
  - mock / 后端切换
  - 接口路径管理
  - 参数透传
  - 响应结构兼容
  - 字段映射或标准化
- 当接口可能返回两种结构时，默认兼容：
  - 直接返回业务对象
  - 返回 `{ data: 业务对象 }`
- 如果某个页面存在分页、加载更多、搜索、分类筛选等能力，mock 和真实接口都应尽量走同一套 service 入参和返回结构。
- 分页接口默认优先抽象出清晰的分页返回结构，例如：
  - `list`
  - `page`
  - `pageSize`
  - `total`
  - `hasMore`
- 页面中如果存在“加载更多”“搜索联动”“分类联动”，不要只写前端临时切数组逻辑，优先按未来可切真实分页接口的方式组织代码。
- 对于文章点赞、收藏、分享、评论数等交互数据，也不要只写死在组件里，优先抽到独立 service 层处理中。
- 交互类 service 默认也要考虑 mock 与真实接口双模式：
  - mock 模式下可以使用 `localStorage` 或内存态模拟
  - 真实模式下预留后端接口路径
- 与本地存储相关的逻辑，不要散落在多个页面和组件中，优先集中在对应 service 内处理。
- 如果后续接真实接口，优先保证页面和组件无需大改，只替换 service 内部实现。
- 如果一个页面模块已经采用了 mock / service / type 的组织方式，后续同类页面也应复用这套模式，避免项目内部风格不一致。

## Working Style

- 修改代码时，先判断这次变更应该落在哪个模块，再开始写代码。
- 写样式时，先看是否已有全局变量；没有再补，不要直接写死色值。
- 写组件和页面时，必要时添加中文注释，解释模块作用和关键逻辑。
- 做页面时，默认同步考虑桌面、平板和手机，不把适配留到最后补救。
- 写响应式样式时，优先复用项目既有断点，不随意新增零散尺寸。
- 做功能时，默认考虑游客、普通用户和管理员三类角色，不只从单一页面视角出发。
- 如果新增规则与旧规则冲突，以“更利于长期维护”的方案为准，并同步更新这份 skill。
